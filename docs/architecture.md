# Архитектура

Текущий сценарий — запуск уже установленной Tiny11 с Claude Desktop, Firefox
и существующей локальной учётной записью. Пользователь работает через
`Launcher.exe`; Linux остаётся скрытым.

| Часть | Реализация |
|---|---|
| Панель | C#, WPF и WPF-UI (встроен в `Launcher.exe`), системный .NET Framework 4.8 |
| Управление | Встроенный Python 3.12.14 и служебные PowerShell-сценарии |
| Виртуализация | Переносимый QEMU 11.1.0, WHPX |
| Рабочая VM | Tiny11, постоянный QCOW2 и UEFI variables |
| Шлюз | Подготовленный Debian с sing-box, без видимого окна |
| Подключения | Hysteria2, SOCKS5, HTTP и HTTPS CONNECT |
| Сеть Windows | e1000 NIC, локальный QEMU stream к LAN шлюза |
| Файлы ПК (по выбору) | Второй e1000 NIC: QEMU user `restrict=on`, один guestfwd на локальный SMB |
| Внешняя сеть шлюза | QEMU user NAT, без bridge/TAP/hostfwd/guestfwd |
| Защита сети | Закрытая политика nftables, без прямого fallback |

## Панель и состояние

`launcher-wpf\Bridge.cs` вызывает `scripts/portable_app.py` через встроенный Python с
изолированными параметрами запуска (`-X utf8 -I -S -B`). Окно имеет фиксированный размер
клиентской области. Главная страница показывает состояние, выбранное подключение и запуск;
подключение, настройки, проверки и справка открываются со страницы и листами снизу.
Восстановление Python/QEMU и подготовка host-компонентов доступны через PowerShell без
рабочего Python.

Смена страницы не запускает повторную диагностику, если результат уже получен.
Начальные данные настроек берутся из первого отчёта, последующие чтения объединяются
в один запрос. Страница загружается целиком; черновики не заменяются поздним ответом.
Навигация доступна во время операций, сохранение и запуск остаются под общей блокировкой.
Настройки сохраняются автоматически. Визуальная приёмка новой сборки остаётся за владельцем
и не заменяется успешной компиляцией. Автоматических тестов самого WPF-интерфейса нет
(wcp-vuv.10.1): общие исходники `ui\ReleaseInfo.cs` и `ui\PortableEntry.cs` проверяют
`tests\ReleaseInfoRegression.cs` и `tests\PortableEntryRegression.cs`.

После успешного запуска панель сворачивается в трей. Значок Launcher.exe один раз переводится в видимую
область трея (`TrayPromotion.cs`: запись `IsPromoted` в `HKCU\Control Panel\NotifyIconSettings`, значение
пользователя не перезаписывается). Скрытая панель возвращается сама только при подтверждённой проблеме
(`AttentionPolicy.cs`): остановка или сбой VM два опроса подряд, нечитаемое состояние четыре опроса подряд,
неподтверждённая операция сразу. Одиночный сбой опроса окно не показывает. Причины скрытия и показа
пишутся в `logs\launcher-ui.log`.

Видимые настройки ресурсов — память Windows и число процессоров каждой VM.
Служебные память шлюза и LAN-порт сохраняются в конфигурации для совместимости.
Настройки ресурсов применяются при следующем запуске. Повреждённый файл настроек
не перезаписывается без сохранения его исходных байтов рядом.

Профили подключения хранятся отдельно от дисков и компонентов. Секреты защищены
DPAPI пользователя основной Windows. Сохранённый или выбранный профиль не меняет
работающий шлюз: его версия применяется в следующем сеансе. После переноса
на другой ПК программа может запросить повторный ввод секретов.

Внешний трафик шлюза использует только IPv4: DNS не выдаёт AAAA, буквальные
IPv6-адреса отклоняются, пересылка IPv6 через туннель запрещена. Внутренний IPv6
Windows не отключается: локальные ULA-адреса, обнаружение соседей и DNS остаются.
Объявления IPv6 имеют нулевой срок жизни маршрутизатора, поэтому не создают
внешний маршрут. Связанные с соединениями сообщения ICMP о размере пакета
возвращаются в LAN, чтобы IPv4 корректно учитывал MTU туннеля 1280.

## Запуск и выключение

Сначала контроллер проверяет компоненты, ресурсы и выбранное подключение, затем
запускает шлюз с одноразовым слоем записи. Готовность относится к текущему сеансу,
версии профиля и версии шлюза. Только после неё запускается Windows. Старый
маркер сетевой приёмки не доказывает готовность нового сеанса.

Windows получает сеть только через шлюз. Ошибка подключения не разрешает прямой
выход. Шлюз повторяет проверки и восстанавливает соединение при временном обрыве;
проверка управляемого стенда не заменяет приёмку всех поддерживаемых протоколов.

Штатная остановка выполняется в порядке Windows, затем шлюз. Закрытие панели
не завершает VM. Повторный запуск панели должен восстановить отображение реального
состояния процессов. При неопределённом результате выключения пользовательская
Windows сохраняется работающей; автоматическое принудительное завершение запрещено.

При активной VM крестик скрывает панель в трей и сохраняет выбор пользователя.
Фоновый статус, ошибка чтения и поздний результат запуска обновляют данные,
но после ручного закрытия не открывают окно. Этот запрет снимается явным действием
в трее. Автоматическое скрытие панели после успешного запуска имеет другую причину:
после него остановка или ошибка сеанса по-прежнему могут вернуть панель.
Если VM уже остановлена и незавершённого запуска нет, крестик завершает лаунчер.

Компоненты runtime и шлюза заменяются отдельно от пользовательского Windows-диска.
Восстановление приложения не означает восстановление повреждённых данных Windows.
Во время обычной работы host-сеть, Defender, VBS и параметры Hyper-V автоматически
не перенастраиваются. Подготовка требуемого host-компонента — отдельное действие с UAC.

## Окно Windows и описания оборудования

Размером обычного окна управляет только SDL-бэкенд QEMU. Он берёт пропорции
фактической DisplaySurface, физическую рабочую область текущего монитора и рамку.
Контроллер читает фактический размер и один раз размещает окно; он не подгоняет его
под запрошенное разрешение. Запрос режима и подтверждённый режим гостя — разные данные.
При несовпадении пропорций монитора и гостя полный экран сохраняет поля.

Нельзя возвращать периодический внешний `SetWindowPos` для размера: он конкурирует
с SDL, которая хранит свой размер и ограничивает фиксированное окно. Для диагностики
в stderr QEMU записываются `surface`, размер клиента до изменения, `target`, `usable`
и дисплей; контроллер сохраняет измеренные `client`, `outer`, `fits_work_area`.
Поля по бокам при фактическом госте 4:3 и ошибочно заданном окне 16:9 — ожидаемый
результат сохранения пропорций, а не доказательство ошибки DPI.

Отдельный случай — поля уже внутри DisplaySurface: сохранённый рабочий стол Windows
1280×800 вписывается в видеосигнал 1920×1080 с полосами по 96 пикселей. Это видно
в исходном QMP screendump и не исправляется размером SDL-окна. Нужно сохранить
1920×1080 в самой Windows и проверить полный цикл выключения и запуска.
Подготовка, обслуживание и проверка эталона задают тот же стандартный VGA-режим
через `windows_guest_settings.vga_arguments(DEFAULTS)`; обычный запуск использует
выбранные пользователем настройки. После нормализации существующего эталона
для выпуска нужны отдельный standalone-образ и его новые SHA256; старый ZIP
не получает исправление от изменения исходников или рабочей копии.

При смене разрешения одного VGA-режима недостаточно: гостевой `HostFilesGuest`
читает `WCPSETTINGS`, применяет и сохраняет режим Windows и сообщает фактический
размер через COM1. Он доставляется и при выключенном доступе к файлам ПК.
В профиле должен быть один принадлежащий приложению ярлык автозапуска.
`Install-GuestHelper.ps1` устанавливает его в явно подключённую офлайн-копию VHDX,
сохраняя прежние бинарники. Проверка гостя использует ACPI QEMU из прошивки,
а не производителя SMBIOS: описательная метка Dell не должна блокировать помощник.
При первом успешном применении помощник отключает таймеры экрана и сна
в текущей схеме питания гостевой Windows, для сети и батареи (`powercfg /change`, значение `0`).
Отметка `power-defaults-v1.ok` в его пользовательском каталоге не зависит от версии
приложения: последующие запуски и обновления сохраняют ручной выбор пользователя.
Новая выбранная пользователем схема также не переопределяется. При отказе команды
отметка не создаётся, появляется предупреждение, а файлы и буфер продолжают работу.
Настройка выполняется после проверки гостевой среды и подтверждения передачи управления;
схема питания основного ПК не изменяется.
Колонки и микрофон используют поставляемый SDL с отдельными входным и выходным
голосами и картой `hda-micro`. Микрофон выбирается в основной Windows до запуска гостя;
для доступа должны быть разрешены классические приложения в настройках микрофона хоста.
Драйвер DirectSound внутри SDL выбирается явно: без микрофона он сохраняет запуск
и выход звука. Собственный бэкенд `dsound` QEMU 11.1 завершает запуск при таком отказе,
а автоматический выбор WASAPI внутри SDL задерживает повторные попытки открытия.
Гостю передаются только стандартные режимы из `windows_guest_settings.MODES`;
размер клиентского окна и рабочая область монитора не становятся разрешением Windows.
Полный экран сохраняет пропорции рабочего стола. Для монитора 16:9 подходят,
например, 1920×1080 и 2560×1440; стандартный режим 1920×1200 имеет пропорции
16:10 и на таком мониторе оставляет боковые поля.

Описательные поля Windows собраны в `scripts/windows_hardware.py`:

| Поле | Значение и источник |
|---|---|
| Система, плата, корпус | Dell Precision T5500, SMBIOS типов 1/2/3 |
| Имя процессора | Intel Xeon E5620, CPUID brand string модели Westmere |
| Имя IDE-диска | Seagate ST3160815AS, свойство `ide-hd.model` |
| Память и процессоры | Фактически выделенные VM значения настроек |
| Видео и сеть | Прежние std VGA и e1000, прежние драйверы |

Строки не меняют ISA процессора, PCI-устройства, прошивку EDK II, объём диска или
его содержимое. ST3160815AS — модель диска на 160 GB, но доступная гостю ёмкость
по-прежнему задаётся существующим qcow2 (сейчас 80 GiB). Серийные номера и UUID
не заменяются; reference-операции сохраняют собственные уникальные serial.
Источники профиля: [Dell T5500 / E5620](https://www.dell.com/support/home/en-tc/drivers/driversdetails?driverid=d979y),
[Intel E5620](https://www.intel.com/content/www/us/en/products/sku/47925/intel-xeon-processor-e5620-12m-cache-2-40-ghz-5-86-gts-intel-qpi/specifications.html),
[Seagate Barracuda 7200.10](https://www.seagate.com/staticfiles/support/disc/manuals/desktop/Barracuda%207200.10/100402371h.pdf).

## Файлы ПК в Windows

Режимы «Все доступные диски ПК», «Только выбранные папки» и «Выключено» хранятся в
`config/files.json` (по умолчанию выключено) и применяются при следующем запуске.
`HostFiles.exe` (SMBLibrary, SMB2 с обязательной подписью, NTLMv2, одноразовые
логин и пароль сеанса) слушает только 127.0.0.1 и живёт вместе с контроллером
Windows, а не с панелью. Windows видит его как `\\192.168.234.4` через отдельный
NIC без маршрута наружу: `restrict=on` пропускает только этот guestfwd, поэтому
файловый канал не может обойти VPN.

Файловый NIC запускается отключённым (`set_link` до `cont`). Помощник в Windows
задаёт ему постоянный адрес 192.168.234.15/24 без шлюза и DNS (`netsh … store=persistent`
на отключённом адаптере сохраняется и применяется при подключении), затем просит связь
через COM2 (`NIC_STATIC`), и только тогда контроллер её включает. После проверенного
подключения помощник запоминает этот адаптер; при следующих входах связь запрашивается
только для запомненного адаптера, поэтому новый или сброшенный адаптер не получает
от этой сети маршрут по умолчанию или DNS. Помощник сам запускается при входе. Первый раз,
когда в настройках включены файлы ПК, он один раз просит разрешение администратора
(`--configure-nic`, окно Windows) для настройки адаптера, отдельный сценарий запускать не нужно.
Дальше он подключает диски без вопросов. Встроенные в Windows недостижимые
IPv6-DNS `fec0:0:0:ffff::1–3` готовности не мешают.

## Общий буфер обмена

Текст копируется между ПК и Windows в обе стороны. Контроллер добавляет гостю третий COM-порт
(`isa-serial`, IRQ 5, свой, чтобы не делить линию с COM1 и COM2), его QEMU отдаёт как сокет на
127.0.0.1. `scripts/clipboard_bridge.py` подключается к сокету, слушает буфер ПК скрытым окном
(`WM_CLIPBOARDUPDATE`) и передаёт строки JSON с nonce сеанса: сжатый UTF-8, до 256 тыс. символов.
Гостевой помощник (`guest/GuestClipboard.cs`) остаётся в памяти после входа и делает то же в
Windows. Копии, помеченные менеджерами паролей как скрытые, не передаются; собственная запись
не отправляется обратно. Картинки и файлы не передаются. Выключатель в настройках
(`viewer.json`, `share_clipboard`) действует при следующем запуске Windows.

Даже в режиме всех дисков сервер не пускает гостя в папку программы, её
служебные данные в `%LOCALAPPDATA%\WindowsClaudePortable` и папки автозагрузки:
проверка идёт по идентификатору NTFS каждой папки пути, поэтому короткие имена,
регистр и ссылки её не обходят, а родительские папки нельзя переименовать или
удалить. Остальные файлы ПК, доступные учётной записи, в этом режиме меняются
из Windows по-настоящему — это осознанный выбор пользователя в настройках.

## Границы исходников и поставки

Git содержит исходники и проверки, но не VM, runtime, пароли или журналы.
Готовая поставка использует явный перечень файлов и самостоятельные QCOW2 без
внешних backing-файлов. Public-архив не включает host-профили, но не очищает
содержимое Windows-диска: его пригодность проверяется отдельно.

Старые `Start.cmd`, install/resume-ветки и материалы `guest/reference/` и
`guest/template/` остаются историческими средствами подготовки. Для обычного
запуска готовой Windows используются `Launcher.exe` и штатный runtime-путь.
Audit/Sysprep, создание пользователя из EXE и установка VPN на пустой VPS
исключены из текущего объёма.

Приёмка окончательного пакета и перенос на другой ПК ещё не объявлены завершёнными.
