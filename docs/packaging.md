# Выпуск одним ZIP

Готовая поставка — `Pocket-Windows-<версия>.zip` и файл `.sha256`.
Распакуй ZIP Проводником в новую папку, затем открой `Pocket-Windows\Launcher.exe`.
Ярлык этой копии создаётся строкой «Ярлык на рабочий стол» на главной странице. Уже существующий ярлык не заменяется.
Setup для нового выпуска не собирается и не требуется.

В основном образе заранее установлен `HostFilesGuest` с одним ярлыком автозапуска
пользователя. После входа он сам применяет выбранное в панели стандартное разрешение
и сохраняет его для следующих запусков, в том числе при выключенном доступе к файлам ПК.
Для полного экрана выбирай режим с пропорциями монитора: например, 1920×1080
или 2560×1440 для 16:9. Режим 1920×1200 имеет пропорции 16:10.

В архиве нет подключений владельца, путей его папок, журналов и тестовых дисков.
Экспорт подключения содержит секреты: храни его отдельно и импортируй только в свою копию.
«Диагностика» и первый запуск сверяют исходные файлы по внутреннему MANIFEST.
После успешной первичной проверки сохраняется отметка; изменившийся пользовательский
диск с исходным образом больше не сравнивается. Настройки и импортированные подключения
можно менять до первого запуска. Прежние комплекты без нового проверяющего модуля
обрабатываются как legacy и не получают новой отметки целостности.
Файлы `.sha256` защищают
от повреждения; они не являются цифровой подписью издателя.

## Подготовка компактного эталона

Принятый исходный `ready-*` не изменяют: на него ещё ссылается старая QA.
Для обслуживания создают самостоятельную копию `compact-master-<версия>` с файлами
`candidate.qcow2` и `vars.fd`. Первое пересжатие zstd само по себе не означает
очистку Windows или приёмку нового эталона.

Из корня исходников подготовь отдельный носитель (VM не запускается):

```powershell
$copy = '<Служебное>\compact-master-<версия>'
& '.\runtime\python-3.12.14\python.exe' -X utf8 -I -S -B '.\scripts\prepare_compact_master.py' `
  --project (Get-Location).Path --master $copy `
  --maintenance-script ((Get-Location).Path + '\guest\maintenance\Compact-Windows.ps1')
```

Владелец повторяет эту команду с `--run`, открывает внутри копии съёмный носитель,
запускает `RUN.CMD` и подтверждает UAC. Носитель доступен только для чтения.
Гость отключён от сети; скрипт отказывает вне VM с точным SMBIOS-маркером обслуживания.
Он отключает гибернацию, сохраняет принятое хранилище компонентов, чистит
старые временные файлы и кэш загрузок обновлений, восстанавливает состояния служб,
затем выполняет ReTrim. Повторный DISM `/StartComponentCleanup /ResetBase` на этом
эталоне вызвал `CRITICAL_SERVICE_FAILED (0x5A)` при следующей холодной загрузке,
в том числе после восстановления точного нативного SYSTEM и его журналов.
Этот этап исключён; отчёт явно содержит `component-store-preserved`.
Скрипт не удаляет приложения и профили.

Отчёт записывается в `C:\ProgramData\WindowsClaude-compact-*.json`. При ошибке
не считай очистку выполненной. После успешного отчёта штатно выключи Windows через «Пуск».

Для автоматического обслуживания существует отдельный путь `automatic-maintenance-<nonce>`
внутри этой копии: `Service-CompactMaster.ps1` подключает только её временный VHDX без буквы,
а `run_compact_vm.py` запускает гостя без сети со штатными настройками памяти и CPU.
Временная служба проверяет SMBIOS и SHA скрипта, выполняет очистку и выключает гостя.
Перед offline-изменениями удаляется `hiberfil.sys` только в этой копии: быстрый запуск
иначе восстанавливает старый кэш ядра и теряет внесённые изменения. Перед отключением VHDX
хост явно сбрасывает файловый кэш. Первый запуск обслуживания должен быть холодным.
Хост требует успешные отчёты службы и скрипта вместе с QMP `guest-shutdown` и кодом 0.
Режим `Collect` сохраняет отчёты снаружи гостя и удаляет служебный bootstrap перед упаковкой.
Если служба уже удалила свой ключ, `Collect` сохраняет SYSTEM и его журналы без перезаписи.
Изменения SYSTEM выполняются через Windows Offreg в памяти, без загрузки в реестр хоста.
Сначала `recover_compact_hive.py` применяет сохранённые транзакционные журналы и проверяет
целостность дерева. Для этого только в служебной operation нужен архив
[YARP 1.0.33](https://github.com/msuhanov/yarp/tree/1.0.33) с SHA256, закреплённым в скрипте.
Он не устанавливается в систему и не входит в публичную поставку. Исходные SYSTEM и журналы
сохраняются снаружи диска; перед атомарной заменой проверяется, что они не изменились.

Затем на остановленной копии выполняют окончательный `qemu-img convert -c -O qcow2
-o compression_type=zstd`, `qemu-img check`, проверку загрузки и штатного выключения.
Только после принятия нового диска закрепляют его SHA256 и SHA256 UEFI в `MASTER_HASHES`
в `scripts/release_portable.py`. Старые pins не обходят для промежуточной сборки.

Для установки помощника в новую офлайн-копию используется `Install-GuestHelper.ps1`
с явными `-ImagePath`, `-WindowsRoot` и `-HelperPath`. VHDX уже должен быть подключён
без буквы, а его раздел Windows — в `mounted-windows` рядом с VHDX. Скрипт проверяет
принадлежность раздела этой копии и устанавливает один ярлык в существующий профиль;
оригинальный эталон и рабочую Windows для этого не подключают. После установки нужны
сброс кэша, отключение VHDX, пересжатие, проверка совпадения данных и два холодных запуска
с квитанцией COM1 и штатным выключением. Носитель проверки должен содержать ту же новую
версию помощника: устаревший `HostFilesGuest.exe` на нём заменит установленную версию.
Оба запуска выполняет `scripts\verify_master_helper.py` на одноразовом overlay: стандартные 4096 МиБ,
без сети, строки прошивки на COM1 пропускаются, питание нажимается после паузы на рабочем столе
(сразу после квитанции Windows может игнорировать кнопку питания). Пример:
`python -X utf8 -I -B scripts\verify_master_helper.py --source . --master <compact-master> --output <новая папка> --helper-sha256 <SHA256 HostFilesGuest.exe>`.

Обычные запуски Windows передают `discard=unmap`. TRIM освобождает qcow2-кластеры;
немедленное уменьшение физического файла на хосте не обещается. Для первоначального
уменьшения всё равно нужно окончательное offline-пересжатие.

## Сборка из одного коммита

Подготовленный runtime в исходниках обязателен: чистый Git clone не содержит Python,
QEMU и дисков. Перед сборкой должны пройти затронутые проверки и ревью. Изменения
коммитят локально; `prepare` отклоняет незакоммиченные исходники и посторонние C#-входы.

```powershell
$release = '<Служебное>\release-<версия>'
$master = '<Служебное>\compact-master-<версия>'
& '.\runtime\python-3.12.14\python.exe' -X utf8 -I -S -B '.\scripts\release_portable.py' prepare `
  --source (Get-Location).Path --output $release --master $master --release-id <версия>
& '.\runtime\python-3.12.14\python.exe' -X utf8 -I -S -B '.\scripts\release_portable.py' package `
  --release $release --source (Get-Location).Path --master $master
```

`prepare` сверяет принятые hashes диска/UEFI и компонентов, компилирует только Launcher,
формирует общий `app/` и паспорт `RELEASE.json`. `package` собирает чистую `public/`
из этого коммита, принятого master и проверяемого шлюза. Шлюз сначала восстанавливается
из служебной recovery-копии в `app/`, но её дубликат `runtime/gateway-recovery.zip`
и каталог recovery не входят в публичный ZIP. QCOW2 в публичном ZIP сохраняются без
повторного сжатия. Остальные проверки состава, CRC и SHA256 остаются обязательными.

Кнопка восстановления шлюза в новом компактном комплекте сообщает, что нужен исходный
ZIP этого выпуска. Старые комплекты с полным recovery-пакетом продолжают восстанавливаться.
Не удаляй рабочую Windows или подключения при таком сообщении.

## Приёмка и выдача

Новый ZIP с пометкой интернета распаковывают Проводником в отдельную тестовую папку.
Готовую распаковку можно проверить без графики теми же двумя холодными запусками:
`verify_master_helper.py --source <распакованная папка> --output <новая папка> --helper-sha256 <SHA256>`
(без `--master`; берутся её `images\workvm-empty.qcow2`, `state\workvm-vars.fd` и `runtime`).
Владелец проверяет Launcher, вкладки, крестик, диагностику, подготовку ПК и восстановление,
а также запуск Windows, Claude, Firefox, импорт подключения, мышь, полный экран и оба монитора.
Тесты и компиляция не подтверждают эту живую приёмку. Второй ПК пока не проверен.

После явного подтверждения владельца:

```powershell
& '.\runtime\python-3.12.14\python.exe' -X utf8 -I -S -B '.\scripts\release_portable.py' publish `
  --release $release --target '<Выпуск>' --owner-accepted
```

Команда проверяет точную версию/коммит и сохраняет паспорт приёмки в служебной папке.
В «Выпуск» попадают только ZIP и SHA256; инструкция и сведения о компонентах находятся
внутри ZIP. Предыдущая папка
назначения сохраняется отдельно; cloud upload и Git push не выполняются. ZIP и SHA256
владелец загружает на Google Диск. Старые ZIP, Установщик, QA и master удаляются только
после этой приёмки по отдельно подтверждённому списку.

## Личные резервные копии и старые установки

`pack_existing_runtime.py --project <копия> --output <новый.zip>` по умолчанию сохраняет
личные настройки и зашифрованные профили. Такой архив нельзя выдавать другим. Для общего
комплекта обязателен `--mode public`. При существующем выходном файле упаковщик отказывает.
Проверка совместимости со старыми архивами Setup осталась только в Python-коде упаковщика;
сам Setup и его тесты удалены, новый выпуск его не использует. Безопасный app-only updater/rollback сохранён для существующих
пользовательских копий: он не заменяет диски, UEFI, настройки и профили.
Для компактного нового ZIP проверка MANIFEST обязательна, включая случай прерванной
распаковки, при которой ещё не записаны оба файла манифеста. Первый новый формат
начинается с версии 2026.10.23.2. Обновлятор сохраняет прежний режим только для уже
существовавших старых копий; такая отметка не объявляет старый диск проверенным.

## Выключение сеанса

«Выключить Windows» завершает Windows и шлюз, оставляя панель. Пункт трея
«Выключить Windows и выйти» закрывает лаунчер только после подтверждения завершения сеанса.
После аварийного выхода Windows действие «Завершить прерванный сеанс» проверяет оставшиеся
процессы и возвращает возможность запуска. Если Windows не отвечает после штатного ожидания,
доступно отдельное принудительное завершение с подтверждением: несохранённые данные могут
быть потеряны. При неподтверждённой принадлежности процесса он сохраняется, причина доступна в диагностике.

## Обновление приложения через GitHub Releases

Лаунчер проверяет обновления при запуске и затем раз в 6 часов.
На главной всегда доступен раздел «Обновления» с текущей версией, проверкой и установкой.
«Клавиши» находятся в «Характеристиках» и также открываются клавишей F1.

### Подписанный манифест (лаунчеры после 2026.10.30.2)

Издатель определяется ключом, а не адресом. Лаунчер читает `update-manifest.json`
(конверт `{"manifest": base64, "signature": base64}`, подпись ECDSA P-256/SHA-256)
из источников по порядку: `config/update-sources.json` (необязательная ручная замена),
`state/update-feeds.json` (список `feeds` из последнего проверенного манифеста) и
встроенные адреса (`releases/latest/download/update-manifest.json` на GitHub и копия на VPS).
Принимается самый новый манифест с подписью одного из двух закреплённых ключей и версией
не ниже установленной. Ссылки на файлы могут вести на любой HTTPS-хост: размер и SHA-256
берутся только из подписанного манифеста. GitHub API, файлы `.sha256` и ник владельца
новый лаунчер не использует. Поэтому переименование, перенос репозитория или новое
зеркало требуют только правки `scripts/update_sources.json` и нового выпуска;
список `feeds` из манифеста сам переносит уже установленные копии. Манифест со схемой
новее поддерживаемой не угадывается: пользователь получает просьбу скачать полный комплект.
Неизвестные поля игнорируются. Подробности последней проверки: `logs/update-check.txt`.

Ключи лежат в хранилище CNG учётной записи владельца: `PocketWindowsUpdate-A` (основной,
без экспорта) и `PocketWindowsUpdate-B` (резервный, экспортируемый). Их открытые части
закреплены в `launcher-wpf/AppUpdate.cs` и `scripts/update_sources.json`; тест следит,
чтобы списки совпадали, а `prepare` отказывает при ключах-заглушках. Резервный ключ
владелец один раз выгружает на офлайн-носитель:

```powershell
$k = [System.Security.Cryptography.CngKey]::Open('PocketWindowsUpdate-B')
[IO.File]::WriteAllBytes('<офлайн-носитель>\PocketWindowsUpdate-B.pkcs8', $k.Export([System.Security.Cryptography.CngKeyBlobFormat]::Pkcs8PrivateBlob))
```

Потеря обоих ключей отрезает все копии от автообновления: останется только ручная загрузка.
Новые ключи создаёт `release_portable.py keygen --key <имя> [--exportable]`.

После `app-package` и `v2-package` подпиши выпуск, затем загрузи `update-manifest.json`
в GitHub Release вместе с остальными файлами и ту же копию на VPS
(`https://188.130.234.243:8443/pocket-windows/update-manifest.json`):

```powershell
& '.\runtime\python-3.12.14\python.exe' -X utf8 -I -B .\scripts\release_portable.py sign-manifest `
  --release '<Служебное>\release-<версия>'
```

### Устаревший набор для лаунчеров до 2026.10.30.2

Лаунчеры 2026.10.30.x ищут выпуск через GitHub API `TheFactChain/pocket-windows` и проверяют
префикс адреса. Пока такие копии существуют, выпуск публикуется в этом репозитории и содержит
прежний набор: `Pocket-Windows-<версия>-app.zip` и `Pocket-Windows-<версия>-app.zip.sha256`.
Через него они один раз получают новый лаунчер. Копии 2026.10.29.3 и старше проверяют старый
ник `nekontritce11123-lab` и автоматически не обновятся: им нужна ручная установка полного комплекта.

Для совместимости со старыми лаунчерами сохраняется полный пакет файлов программы.
Вместе с ним `app-package` создаёт индекс `Pocket-Windows-<версия>-update.json`
и его `.sha256`. В GitHub Release загружаются все четыре файла. Диск Windows
в пакет приложения не входит:

```powershell
& '.\runtime\python-3.12.14\python.exe' -X utf8 -I -B .\scripts\release_portable.py app-package `
  --release '<Служебное>\release-<версия>'
```

После проверки эти файлы публикуются в GitHub Release с тегом `v<версия>`;
создание пакета само по себе ничего не публикует. Начиная с 2026.10.26.2, лаунчер
проверяет SHA256 индекса и фактические файлы установки. Совпадающие файлы не
скачиваются; отсутствующие, повреждённые и новые загружаются диапазонами полного ZIP.
Для каждого диапазона обязательны HTTP 206, точный Content-Range, размер и SHA256
распакованного файла. Если сервер проигнорировал диапазон, загрузка останавливается
без скрытого скачивания полного архива.

Из проверенных данных создаётся локальный пакет для прежней транзакционной
установки с откатом. Пропущенные файлы повторно проверяются перед закрытием панели
и ещё раз под блокировкой установки. Локальный носитель восстановления шлюза
при необходимости включается из уже проверенных файлов без повторной загрузки.
`--base` остаётся для ручного обслуживания. Старый лаунчер один раз получает
полный переходный пакет; следующие обновления используют индекс.

### Формат v2: части, продолжение и автономное восстановление

Новый клиент предпочитает `Pocket-Windows-<версия>-update-v2.json` и его SHA256.
Манифест связывает выпуск, минимальную версию обновлятора, файлы, их SHA256 и
последовательности частей по 4 МиБ. Каждая часть сжимается независимо в
`Pocket-Windows-<версия>-chunks.zip`. Образ шлюза режется до сжатия; прежние
recovery ZIP в логический состав v2 не входят. Полный `-app.zip` и индекс v1
сохраняются для старых клиентов и отдельного явно выбранного полного скачивания.

Сначала подготовь полный комплект общего доступа штатным `Build-HostFiles.ps1`
из закреплённого upstream-архива. Передай его папку в `prepare --components`.
Сборка проверяет хэши host/guest исходников, процедуры сборки и каждого результата:
прежний manifest без происхождения или устаревший EXE не принимаются.
Выпуск собирается из чистого коммита. После обычного `app-package` добавь v2:

```powershell
& '.\runtime\python-3.12.14\python.exe' -X utf8 -I -B .\scripts\release_portable.py v2-package `
  --source '<Исходники>' --release '<Служебное>\release-<версия>'
```

В релиз входят обе пары индексов, полный app ZIP, chunks ZIP, updater ZIP и их
SHA256. Независимый `-updater.zip` содержит Python, необходимые скрипты, лицензии
и инвентарь; он проверяется до запуска и не зависит от установленного Python.
Для переходного выпуска используй `prepare --bridge <проверенный выпуск>`:
Python, QEMU, шлюз и файловые компоненты копируются строго по хэшам базы;
`bridge_base` фиксирует это намеренное сохранение компонентов. `--components`
и `--bridge` вместе запрещены. Следующий обычный выпуск уже использует свежие компоненты.

В разделе обновлений остаются две кнопки: «Проверить» и «Обновить».
Загрузка и установка доступны после выключения Windows. Одно нажатие «Обновить»
выполняет подготовку, загрузку и установку; размер и свободное место проверяются
внутри операции. Интерфейс показывает короткий статус и ход работы. Проверенные части
хранятся в `state/update-cache/chunks`; отмена не удаляет их. Неоконченная часть
скачивается заново, готовая повторно проверяется. Сервер, игнорирующий Range,
не вызывает скрытого полного скачивания. При ошибке выборочной загрузки полный
пакет предлагается отдельным диалогом с размером; без подтверждения он не загружается.

Из частей собираются непосредственно файлы одноразового `state/<uuid>`.
Инвентарь установки и текущий каталог восстановления переключаются той же
транзакцией; старые recovery ZIP удаляются только после полной проверки кэша.
Полный пакет v2 сначала заполняет этот же кэш из проверенной распаковки и проходит
тот же путь установки. При обычном полном пакете v1 прежний активный v2-каталог
отключается транзакционно, чтобы восстановление не вернуло старую версию.

Журнал v3 остаётся активным до пробного запуска новой панели. Панель в этом режиме
не запускает VM и не меняет настройки; настоящий backend проверяет выпуск и файлы.
ACK связан с nonce, корнем, PID и временем запуска. Без ACK за 120 секунд обновлятор
закрывает только собственную пробную панель и откатывает изменения. Если сам
обновлятор аварийно завершился, неподтверждённая панель тоже закрывается по таймеру,
оставляя журнал для штатного восстановления. Диагностический log не является
условием успешного завершения: подтверждение хранится отдельной обязательной записью.

Восстановление через ту же кнопку «Обновить» использует текущий каталог и проверенный
сохранённый комплект обновлятора. В автономном режиме сеть запрещена; недостаточный
или повреждённый кэш даёт явный отказ. После отката комплект выбирается по каталогу
восстановленного выпуска, даже если указатель незавершённой операции относится к новому.
Очистка сохраняет последний рабочий откат, активные операции и используемые части;
неизвестные файлы и непроверенные папки не удаляются. Перенос незавершённой операции
между томами автоматически не принимается. Папку с чрезмерно длинным путём нужно
перенести ближе к корню диска до подготовки.

Небольшие изменения шлюза должны сохранять принятую чистую основу и расположение
данных. Повторная установка Debian может изменить большинство частей: размер
реальной передачи измеряется на готовом образе, малый объём заранее не обещается.

Первый переход с версии 2026.10.24.13 должен менять только уже известные ей пути и сохранять
версии Python, QEMU и шлюза. Этот промежуточный выпуск устанавливает исправленный обновлятор.
Новые модули и новые каталоги runtime разрешены уже после него. Старый обновлятор не умеет
автоматически находить промежуточный выпуск, поэтому при пропуске этого перехода потребуется
установить промежуточный пакет или перенести личную копию по отдельной инструкции.
Версии Python и QEMU названы в одном месте: `scripts/runtime_config.py` (`PYTHON`, `QEMU`) и
`Bridge.PythonDir` в лаунчере; тест не даёт вписать их в код повторно. При смене версий обновляют
эти константы и закреплённые хэши.

Пользователь штатно выключает Windows и нажимает «Обновить». Загрузку и предварительную проверку
можно отменить. До закрытия панели проверяются размер, SHA-256, версия, безопасные пути и полный
состав архива. Во время операции запуск Windows и изменение настроек недоступны. Для новых
лаунчеров SHA-256 берётся из подписанного манифеста; лаунчеры до 2026.10.30.2 сверяют только
опубликованную рядом сумму, которая не является подписью издателя.

Установщик использует отдельную копию Python и скриптов в `state/app-updater-<id>`.
Она сохраняется для восстановления и не заменяется вместе с программой. Установщик ждёт
завершения конкретного процесса лаунчера, повторно проверяет пакет, берёт блокировку и заменяет
файлы через журнал. Перед первой заменой он проверяет, не открылась ли другая панель.
Диск Windows, UEFI, подключения, личные настройки и общие папки ПК не входят в список замены.

Обновляются лаунчер, скрипты, Python, QEMU, компоненты общего доступа и пакет шлюза.
Переключение активной версии шлюза входит в ту же транзакцию. Старые диски шлюза сохраняются.
Гостевой помощник получает новые файлы при следующем входе в Windows через установленную
автозагрузку; отсутствующую или повреждённую автозагрузку этот механизм сам не создаёт.
Удалять устаревший файл можно только если он записан в `state/application-files.json`
и его содержимое не менялось. При первом переходе без такого списка неизвестные файлы сохраняются.

При обычном сбое установщик откатывает заменённые файлы и запускает прежнюю программу.
После прерывания с незавершённым журналом Launcher предлагает восстановить предыдущую версию.
Резервные файлы находятся в `state/app-update-<id>`, сохранённый установщик указан в
`state/update-recovery.json`; до завершения восстановления эти папки нельзя удалять.
Результат записывается в `logs/update-result.json`, подробности ошибки в `logs/update-details.txt`.
Рабочая Windows не запускается, пока существует незавершённый журнал обновления.

Новые операции хранят относительный указатель восстановления и идентичность каталога,
поэтому допускают его переименование на том же томе. Перенесённая незавершённая операция
старой версии 2026.10.25.3 требует полного нового комплекта отдельно: её сохранённый
обновлятор остаётся старым. Закрой панель и VM этой копии, распакуй и проверь новый комплект,
затем запусти его средство отката, не копируя скрипты поверх прерванной установки:

```powershell
$new = '<отдельный проверенный новый комплект>'
$old = '<перенесённая копия с прерванным обновлением>'
& "$new\runtime\python-3.12.14\python.exe" -X utf8 -I -B "$new\scripts\release_portable.py" rollback --target $old
```

Откат проверяет резервные файлы и сохранённые идентичности; при несовпадении сохраняет их
для диагностики. После успешного отката можно открыть Launcher в восстановленной копии.

Для проверки без публикации можно задать `POCKET_WINDOWS_UPDATE_API` с адресом
`http://127.0.0.1:порт/...`. Остальные адреса переопределения игнорируются.
