# Инвентаризация эталонной копии: только фаза 1

Этот пакет собирает материал для решения, пригодна ли **изолированная копия Tiny11** для будущего эталона. Он ничего не удаляет, не меняет пользователей, не запускает Sysprep, не перезагружает Windows и не подключается к сети. Результат не означает готовность эталона.

## Подготовка пакета на стороне проекта

`python scripts/reference_prep.py prepare <новая-папка>`

Команда создаёт четыре файла: этот документ, сборщик, `Run-Inventory.cmd` и `handoff.json`. Манифест содержит SHA256 трёх исходных файлов и случайный публичный `reference_id`. Повторный вызов с неизменённым пакетом возвращает тот же ID и не перезаписывает файлы. Изменённую или постороннюю папку команда отклоняет.

Ответственный за запуск копии должен задать **именно этой VM** SMBIOS type 1 serial, равный `expected_smbios_serial` из манифеста: параметр QEMU `-smbios type=1,serial=WCREFERENCE-<reference_id>`. Это техническая защита от случайного запуска на хосте. Она не доказывает отсутствие сети или подключённых оригинальных дисков: изоляцию копии и отсутствие доступа к исходным дискам проверяют отдельно до запуска. Пакет не запускает VM и не настраивает SMBIOS сам.

## Единственный ручной запуск внутри копии

Внутри изолированной копии под обычным вошедшим пользователем открой диск с пакетом (в том числе readonly QEMU FAT) и запусти **`Run-Inventory.cmd`**, затем подтверди UAC. Это единственное ручное действие запуска.

Bootstrap сначала сверяет реальный SMBIOS и хеши. До этой проверки он ничего не копирует и не запрашивает UAC. Затем копирует три исходных файла и манифест в `%LOCALAPPDATA%\WindowsClaudeReference\<reference_id>` и вызывает встроенный 64-разрядный Windows PowerShell с `-File` и `-ReturnSerial` от имени интерактивного администратора. Уже существующая папка допускается только с теми же четырьмя файлами и хешами; другой файл или готовый отчёт не перезаписывается. Junction/symlink в путях отклоняются.

После UAC доверенная локальная копия `Run-Inventory.cmd` запускает отдельный PowerShell с `-File`. Оба потока вывода дочернего процесса сохраняются **только локально** в `collector-output.log` рядом с пакетом: не более 64 KiB, последующий вывод дренируется без записи. В `collector-exit.json` остаются этап и код завершения. Родительское окно показывает этап, код и пути к этим файлам; при ошибке также сразу выводит сохранённую диагностику и ждёт нажатия клавиши. Обрезанный в конце UTF-8 заменяется читаемым символом замены, код ошибки сохраняется. Отмена UAC показывается как `uac_cancelled`, код 1223; дочерний процесс и его журналы при этом не создаются. Эти файлы не отправляются в COM2 и не добавляются в inventory; не передавай журнал без просмотра. При отказе самого collector в журнал также попадают только фиксированный этап, имя базового типа исключения и числовой HResult; исходные сообщения CIM/registry/Appx не выводятся. Это диагностика запуска, а не исправление причины ошибки. Повторный запуск не перезаписывает существующий отчёт или диагностику.

Не запускай из SYSTEM, службы, Task Scheduler или RunSynchronous. Bootstrap выполняет свой код через `-Command`, а сам коллектор запускает через `-File`. После повторной проверки SMBIOS и SHA256 elevated wrapper читает `Get-ExecutionPolicy -List`. Только при пяти уникальных scope (`MachinePolicy`, `UserPolicy`, `Process`, `CurrentUser`, `LocalMachine`), каждый из которых равен `Undefined`, дочернему PowerShell добавляется `-ExecutionPolicy RemoteSigned`. Это настройка только нового процесса; постоянные политики не меняются. При любой явно заданной политике параметр вообще не добавляется: Restricted, AllSigned и правила GPO сохраняют действие. Неизвестный scope, дубликат, неполный ответ или ошибка запроса останавливают запуск с этапом `policy_query`. Имена scope, значения enum и выбранный режим сохраняются только в локальных `collector-output.log` и `collector-exit.json`; выбранный `execution_mode` также показывается в родительском окне. Если явно заданная политика запрещает скрипт, передай факт отказа ответственному за подготовку. При несовпадении реального SMBIOS serial, неверном хеше, недостаточных правах или существующем отчёте сборщик откажет. UAC может запросить подтверждение или учётные данные администратора; скрипты их не читают и не сохраняют.

Успешный запуск создаёт локальный `reference-report.json` в указанной папке. Передай его для проверки: `python scripts/reference_prep.py review <путь-к-отчёту> --expected-reference-id <ID-из-handoff.json>`. Несовпадающий ID отклоняется. Отчёт содержит имена локальных пользователей, SID и названия программ; это персональные метаданные, не анонимный документ. Не публикуй его без просмотра. Сохранённые пароли, токены, ключи продукта, команды удаления, содержимое браузерных баз и журналов не собираются. Текст произвольных ошибок CIM/registry/Appx не экспортируется; локальный журнал запуска может содержать сообщения PowerShell об отказе политики или ошибке скрипта.

После локального сохранения `-ReturnSerial` передаёт в COM2 ASCII-заголовок `WCREFERENCE <reference_id> <UTF8_byte_length>\n` (LF), затем ровно те же байты JSON в UTF-8 без BOM, без последующих логов. Длина берётся из того же массива байтов, который записан в локальный файл. Параметры порта: 115200, 8N1, без handshake; размер отчёта до 8 MiB, блоки по 4096 байт, тайм-аут записи 1000 мс, общий срок отправки 30 секунд (последняя запись может добавить до 1 секунды). Порт закрывается в `finally`. При ошибке COM2 полный локальный отчёт остаётся на месте; серийные данные могут быть неполными и должны пройти обычную валидацию. Сам сбор метаданных зависит от времени ответа локальных CIM/Appx-команд. Для запуска без COM2 можно вручную вызвать локальный коллектор без `-ReturnSerial` в elevated интерактивном 64-bit PowerShell.

## Что означает отчёт

- `machine_apps`: только записи установки HKLM в обеих разрядностях; portable-программы и все файлы на диске не инвентаризируются.
- `local_accounts`: локальные учётные записи, включая ещё не имеющие профиля: имя, SID, признак отключения. Пароли и их хеши не читаются. Членство всех пользователей в группах этим этапом не устанавливается; elevated admin подтверждается только для текущего контекста.
- `users`: профили Win32_UserProfile с сопоставлением локальных имён/SID; специальные и удалённые/доменные профили могут не иметь имени. Это не перечень всех когда-либо существовавших учётных записей.
- `user_apps`: записи установки только в уже загруженных HKEY_USERS. Чужие NTUSER.DAT не загружаются. При незагруженных профилях результат `partial`; отсутствие строки не означает отсутствие программы.
- `appx` и `provisioned_appx`: метаданные пакетов и состояния установки по SID. Недоступные команды Tiny11 дают `unavailable`, а не пустое подтверждение готовности. Сравнение имени/версии в Python — кандидаты для ручной проверки, не точная модель совместимости Sysprep.
- `markers`: только существование заранее известных каталогов Claude, браузеров, Windows Credentials/Vault/DPAPI и Temp. `true` не доказывает вход или наличие секретов; `false` не доказывает их отсутствие; `null` означает не проверено. Иные каталоги, Roaming Credentials и сторонние менеджеры паролей не охватываются.
- `os`: версия, редакция, наличие установленного Sysprep и известные признаки ожидающей перезагрузки/установки. Это не полная проверка всех требований Windows.

После анализа ещё нужно согласовать список сохраняемых приложений и соответствие профилей, проверить входы и кэш, EFS, лицензии приложений и пригодность изменённого Tiny11. Никакой результат этого этапа не разрешает автоматическую очистку или generalize. Для повторного сбора сначала отдельно сохрани и проанализируй предыдущий отчёт; скрипт его не перезаписывает и не удаляет.

## Основания Microsoft

Пять scope, стандартная Restricted на клиентской Windows, RemoteSigned для локальных сценариев и действие `-ExecutionPolicy` только в новом процессе описаны в [Microsoft: about_Execution_Policies (PowerShell 5.1)](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_execution_policies?view=powershell-5.1).

Sysprep используют для создания образа, из установленной с этой Windows версии. Запуск под SYSTEM и автоматизация через Deployment RunSynchronous не поддерживаются. Шифрованные EFS-данные требуют отдельного рассмотрения; сборщик их не сканирует. [Sysprep overview](https://learn.microsoft.com/en-us/windows-hardware/manufacture/desktop/sysprep--system-preparation--overview?view=windows-11).

Установленные для пользователя Appx, отличающиеся от provisioned пакетов, могут помешать generalize. Документированные способы удаления здесь намеренно не выполняются: решение принимается после отчёта. [Microsoft Store apps and Sysprep](https://learn.microsoft.com/en-us/troubleshoot/windows-client/setup-upgrade-and-drivers/sysprep-fails-remove-or-update-store-apps).

Последствия запуска Sysprep как SYSTEM описаны отдельно: [Microsoft: black screen after Sysprep as SYSTEM](https://learn.microsoft.com/en-us/troubleshoot/windows-client/setup-upgrade-and-drivers/sysprep-as-system-windows-11).
